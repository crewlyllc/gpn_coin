# Release 0.3.66 — how long it took

Raw replay: `0.3.66.json` (`scripts/release-timing.py 0.3.66 --json`), run before the checklist was
moved to `archive/`.

## The replay says 0s — and why that is not a bug in the tool

Every tick of this release landed in one of two commits (`a3a94a1` for the site/doc stamp, and the
run's docs commit), and the replay dates a tick by the commit that introduced it. With a batched
history every box shares one timestamp, so `total: 0s` and every section span is `0s`.

The tool is measuring what it can see. What it cannot see is the order boxes were actually worked in,
because they were not committed as they happened. **This release's timing numbers are therefore wall
clock from the logs, not from the replay.**

## Slowest step, and what shortens it

**§5's Windows build** — 8 h 26 min from dispatch to a concluded job, of which the build itself was
roughly 40 minutes. The rest was queue and runner contention on box 1's single-slot runner. The
shortening already in place is procedural: the loop dispatches and ends the run, so that wait is paid
by a later run instead of by a stalled session. Anything more would need a second Windows runner,
which is a cost decision, not a code change.

Second: **§7's release-cut at 9 minutes**, dominated by uploading 340 MB + 249 MB to the mirror repo.
Not much to win there without changing how the mirror is fed.

## What was re-done (the expensive kind of slow)

- The release-cut had to be re-dispatched once earlier because of the shallow clone
  (`no CI run for commit 1b9ded2 within 25 commits`, fixed with `git fetch --unshallow`).
- `download.html` and `docs/run-a-node.md` were found carrying stale version stamps (0.3.65 / 0.3.64)
  after the cut and had to be fixed in a second commit. A pre-cut check of the three surface files
  would have avoided that entirely — worth adding to the generator rather than relying on §7b to catch it.
