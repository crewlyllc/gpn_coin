Run a node (single command)

GPN ships a single-node supervisor, gpn_node, so an operator runs one command and gets one node — the chain node/miner, the provider heartbeat, and the provider loop(s) — started, logged (one prefixed stream), monitored (one status line) and stopped cleanly, together.

A GPN node is always both a miner and an AI provider. There is no role option and no mine-only / provider-only mode: every gpn_node start brings up the chain node/miner and the AI serving stack. The node mines and serves AI, auto-yielding the one GPU to a job while it runs (mining fully stops for the job's duration, then resumes — see #24).

⚑ “One GPU, one job” = MUTUAL EXCLUSION, not a limit on job types. The single GPU runs exactly one job at a time — never two concurrent — so it never over-subscribes its compute/VRAM. It does NOT mean only some job types are available: every node is equipped by design to serve every job type — LLM chat · image · video · ML inference · fine-tune — and advertises all of them. The scheduler routes each incoming job to a node that can serve it; that node runs that one job to completion (mining paused) before accepting another. All capabilities are ON by default; a constrained box can opt a capability out with GPN_DIFFUSION=0 / GPN_ML=0 / GPN_FINETUNE=0 (or diffusion = false etc. in the config file), but the default is “everything available”.

Internally the parts stay separate processes (fault isolation: a crash in the AI stack cannot take the chain node down), but the operator never has to manage them individually.

Install on a new computer

Three steps, one question.

1. Download + extract
2. ./gpn_node --setup        (answer: generate or import a wallet)
3. ./gpn_node

That is the whole install. Nothing else has to be set: the chain spec, data folder, payout address, peer list and public address are all resolved automatically. --setup also installs/starts ollama and pulls the baseline model, because a GPN node is always miner + AI provider.

Check the version / all options

$ ./gpn_node --version
gpn_node 0.1.0 (spec 41)

$ ./gpn_node --help      # usage, --setup/--version/--help, key GPN_* env vars

Both flags answer immediately and exit 0: no config is read, no data dir is created, nothing is downloaded and no wallet prompt appears. Use them to confirm which build a machine is running before debugging anything else.

1. Download + extract

Grab the release archive for your OS (Linux, macOS, Windows) and unpack it anywhere. It contains gpn_node, gpn-node, the gpn_* agent binaries, the scripts/ folder and gpn-node.example.toml.

3. ./gpn_node

One command starts the miner, the heartbeat and every AI provider, supervised as one node with one log stream and one status line. The second run needs no flags and no environment variables — it reads ~/.gpn/node.toml.

Fallbacks (the rare cases)

  • First run with no internet — the spec fetch fails after ~45 s and the node starts on its built-in testnet spec with a warning. Set GPN_CHAIN to a local spec file if the genesis hash must match a specific network.
  • Router with UPnP disabled — the node prints the NOT-DIALABLE notice with the exact port-forward rule (TCP 30333 → this machine) and exits 78. See Make your node dialable. If the router rewrites the external port, set GPN_PUBLIC_ADDR=/ip4/<ip>/tcp/<port>.
  • CGNAT (100.64.0.0/10 WAN address) — no forward can work; run the node on a host with a public IP, or opt out of the gate with --no-require-backbone (degraded mode).
  • systemd / container / CI (no TTY) — the wizard never hangs: with no wallet configured it exits 2 and tells you to run gpn_node --setup once interactively. After that the service starts with no prompts.
  • Different data disk — set GPN_BASE_PATH (or base_path in the config) before the first run.

Backbone by default — dialable is REQUIRED

Every GPN node is a backbone node: it announces its endpoint, accepts inbound peers, relays and serves blocks for the mesh, and earns the gpn-liveness uptime credit that gates the Silver/Gold staking multiplier. The best nodes become seeds (bootstrap targets) automatically — see How to become a seed.

The network is still growing, so inbound reachability is required by default. A node that cannot be dialled prints the notice below and exits with code 78 (EX_CONFIG, reported as node=down(not dialable)). Nothing is silently half-joined.

Opting out (not recommended while the network is growing). --no-require-backbone (or GPN_REQUIRE_BACKBONE=0) keeps the node running when it cannot be dialled: it prints the same notice and continues in degraded, non-discoverable mode — syncing, mining and serving AI jobs with the same block rewards and job payouts. The only things it does not get are liveness credit, seed-list eligibility, and a small routing tie-break. In this mode it re-checks every 10 minutes and prints NOW DIALABLE once when the forward starts working.

At startup the node probes inbound reachability for up to 120 s (GPN_DIALABLE_TIMEOUT_SECS), in this order:

  1. explicit GPN_PUBLIC_ADDR / --public-addr → match it against what peers report about us, a direct bind, an external STUN binding, or a bounded outbound TCP reachability probe (see the evidence model below);
  2. direct public listen address, libp2p Identify external addresses, or an actual inbound peer on :30333;
  3. UPnP-IGD / NAT-PMP mapping attempt (~10 s) if GPN_UPNP=auto (the default). If the router accepts the rule, its reported external ip:port becomes this node's advertised public address. CGNAT is detected here first: a WAN address in 100.64.0.0/10 (or an RFC1918 WAN address) means no forward can work, and the attempt is skipped;
  4. CGNAT/private WAN → no forward is possible (reported by the notice);
  5. not dialable: print the notice and exit 78 (default), or continue in degraded mode with --no-require-backbone.

Evidence model

The gate passes on any one of these (strongest first):

Evidence Meaning
inbound_peer a peer opened a connection to us
configured_addr_matches_observation our configured GPN_PUBLIC_ADDR endpoint was reported by peers (Identify) as our external address
observed_public_addr no configured address, but peers see us at a public ip:port on our listen port
stun_mapped_addr an external STUN binding says the NAT maps our socket to exactly the configured endpoint
tcp_probe_ok a bounded (5 s) outbound TCP connect to the configured public ip:port succeeded — hairpin, so the weakest signal

/dns4 and /dns6 are first-class public addresses: GPN_PUBLIC_ADDR=/dns4/gpn-testnet.duckdns.org/tcp/30333 is accepted, the name is resolved at check time, every resolved IP must be globally routable, and the resolved IPs (not the hostname) are compared with what peers report.

The gate never halts the chain. Before refusing to start, the node checks whether it is the last authoring node the network can see (0–1 connected peers) or a dev/solo chain. If so it prints DIALABILITY GATE OVERRIDDEN - KEEPING THE CHAIN ALIVE, continues in degraded mode and keeps re-checking. Set GPN_DIALABILITY_SAFETY=0 to force the hard failure anyway. GPN_STUN_SERVER=<host:port> overrides the STUN server (default stun.l.google.com:19302); GPN_STUN_SERVER=off disables that probe.

A successful mapping is not proof of reachability on its own: the gate still waits for an inbound peer (or a matching Identify observation) before the node declares itself dialable. The mapping is renewed at half its lease (default 3600 s) and re-reads the WAN address each time.

Only globally routable addresses count — RFC1918 (10/8, 172.16/12, 192.168/16), CGNAT (100.64/10), loopback, link-local and 0.0.0.0 never do.

Opting out. --no-require-backbone (or GPN_REQUIRE_BACKBONE=0) disables the hard gate: the node logs the same notice and continues as a non-discoverable participant instead of exiting. Use it for a machine that physically cannot be forwarded (CGNAT) and must still run.

Make your node dialable

The walkthrough below is what the notice above tells you to do. You need it on any host that is not already directly reachable on a public IP.

Recommended setup (example)

A setup that works on most home routers, in three steps:

  1. Pin the LAN IP with a DHCP reservation on the router, so the address the forward points at never changes. Example: 192.168.1.50 (the node prints the address it actually detected, which may be e.g. 192.168.1.42).
  2. Forward one port, external = internal: 30333 → 30333. Keeping the numbers equal means no GPN_PUBLIC_ADDR is needed when the probe sees the mapping.
  3. Allow 30333/tcp in the host firewall (commands in step 2 below).

Concrete example rule, as it appears on a typical router page:

Name ............ GPN node
Protocol ........ TCP
External port ... 30333
Internal port ... 30333
Internal IP ..... 192.168.1.50

That is the whole recipe. The rest of this section explains each step and the failure modes (multiple nodes, CGNAT, port rewritten by the router).

1. Forward TCP 30333 on your router

  1. Find this machine's LAN IP: ipconfig (Windows) or ip addr / ifconfig (Linux/macOS). Prefer a DHCP reservation or static lease so it does not change.
  2. Open the router admin page — usually http://192.168.1.1 or http://192.168.0.1; the address is printed on the router label.
  3. Find Port Forwarding (sometimes Virtual Server, NAT, or Games & Applications).
  4. Add a rule: - Protocol: TCP (not UDP) - External / WAN port: 30333 - Internal / LAN port: 30333 - Internal host / IP: this machine's LAN IP (e.g. 192.168.1.42)
  5. Save and reboot the router if it asks.

Running more than one node on the same network? Give each a distinct GPN_SEED_PORT and forward each port to its own machine.

2. Open the host firewall

Forwarding at the router is not enough if the OS firewall drops the packet.

Windows (Administrator PowerShell — note the backtick line continuation):

New-NetFirewallRule -DisplayName "GPN node" -Direction Inbound `
  -Protocol TCP -LocalPort 30333 -Action Allow

Verify: Get-NetFirewallRule -DisplayName "GPN node".

Linux — ufw (Debian/Ubuntu):

sudo ufw allow 30333/tcp
sudo ufw status verbose

Linux — firewalld (Fedora/RHEL/CentOS):

sudo firewall-cmd --add-port=30333/tcp --permanent
sudo firewall-cmd --reload
sudo firewall-cmd --list-ports

macOS: System Settings → Network → Firewall → Options → allow the gpn_node binary (or sudo /usr/libexec/ApplicationFirewall/socketfilterfw --add /path/to/gpn_node).

3. UPnP / NAT-PMP — automatic (on by default)

Most home users do not need step 1. Before the node decides it is not dialable, it asks the router to open the port for it:

  1. UPnP-IGD (SSDP discovery + AddPortMapping TCP 30333 -> this host, lease 3600 s), then
  2. NAT-PMP (RFC 6886, UDP/5351) as a fallback for Apple and other routers that implement NAT-PMP but not UPnP.

Only one TCP port is opened — never UDP, never a range, never a DMZ. The rule is renewed at half-life and expires on its own if the node dies, so a crashed node never leaves a permanent hole in the router.

It is never silent. A successful mapping logs (the log line is the consent record):

portmap: UPnP: mapped TCP 30333 -> 192.168.1.42:30333 via 192.168.1.1 (UPnP-IGD); external address is 23.241.109.255:30333. Disable with GPN_UPNP=off or --no-upnp

and the router-reported external ip:port becomes the node's advertised address — including when the router assigns a different external port (45123 -> 30333 is advertised as …:45123, no GPN_PUBLIC_ADDR needed).

A failed attempt is also logged, and the node falls through to the manual instructions in the notice:

portmap: automatic port mapping FAILED (no gateway: ...); TCP 30333 must be forwarded manually. If your router has UPnP disabled, enabling it - or adding the forward - is the fix.

Turn it off: --no-upnp (or GPN_UPNP=off). The node then never sends a packet to the router and behaves exactly like a manually-forwarded host. Use this if you consider UPnP a security surface you do not want exposed; a manual forward (step 1) is equally valid.

It will not work when:

  • the router has UPnP/IGD (and NAT-PMP) disabled — common on ISP-supplied routers, and the default on many business routers;
  • the WAN address is CGNAT (100.64.0.0/10) or private (double NAT) — detected before the attempt, reported as CGNAT;
  • the router is on a different L2 segment (guest/VLAN isolation, Docker bridge networking, some VPNs) so SSDP never reaches it;
  • Windows: NAT-PMP needs GPN_NATPMP_GATEWAY=<router IP> (gateway detection is implemented for Linux/macOS only; UPnP needs no such hint).

When a mapping succeeds but the node is still not dialable after 120 s, the mapping was accepted but the inbound path is blocked (host firewall, ISP filtering, or the router applied it to the wrong interface). Step 2 (host firewall) is then the usual fix.

Renewal / IP change. The rule is renewed at half the lease. If the ISP changes the WAN IP, or the router assigns a different external port, the new address is logged and used for subsequent checks; the running libp2p instance cannot change its announced address set, so restart the node to advertise the new address. Peers that learn the address through Identify will still find the new path in the meantime.

Re-detection (no restart needed). With no live mapping the node re-runs the whole UPnP-IGD → NAT-PMP ladder every 10 minutes (GPN_UPNP_RETRY_SECS, floor 30 s, cap 3600 s). Three cases this covers, all previously "restart the node":

  • you enable UPnP on the router after the node started;
  • the router reboots or is replaced and drops the rule (the stale handle is discarded and discovery starts over);
  • the WAN address moves off CGNAT (e.g. the ISP hands you a public IP).

If a live rule stops renewing, the node immediately re-runs discovery rather than waiting for the next 10-minute tick. Logging is edge-triggered: a node that stays unmappable says so once (plus a single line when it recovers), never every 10 minutes.

4. CGNAT — when forwarding is impossible

Check the WAN address on the router status page (not the LAN address):

  • 100.64.0.0/10 → carrier-grade NAT. Your ISP does not give you a public IPv4; no port forward can work. Options: ask the ISP for a public/static IP, use IPv6 if your ISP routes a public prefix, or run the node on a cheap VPS.
  • A public WAN address that differs from what a "what is my IP" site reports → also CGNAT (double NAT).

CGNAT is not an error. By default the node exits with the notice (it cannot be a backbone member); with --no-require-backbone it keeps syncing, mining and serving jobs as a non-discoverable participant.

5. Tell the node its public address (only if detection fails)

Auto-detection covers most hosts. Set it explicitly when the router rewrites ports or detection is ambiguous:

# ~/.gpn/node.toml
public_addr = "/ip4/203.0.113.10/tcp/30333"

or:

GPN_PUBLIC_ADDR=/ip4/203.0.113.10/tcp/30333   # env wins over the config file

Use /ip6/<addr>/tcp/<port> for IPv6. The port must be the external port you forwarded, not necessarily the listen port. On a VPS with a directly bound public IP this is usually unnecessary, but setting it is harmless and makes the announced endpoint exact.

6. Verify from outside

The node re-checks every 10 minutes when it is running in the opt-out mode (--no-require-backbone); by default it exits instead, so restart it after the forward is in place. You can also confirm the forward yourself:

  • From another network (phone hotspot, a friend's house, a VPS) — not from the same LAN, where NAT hairpinning can give a false positive:
# Windows
Test-NetConnection <your-public-ip> -Port 30333
# => TcpTestSucceeded : True

# Linux/macOS
nc -vz <your-public-ip> 30333
  • Online port checker (e.g. portchecker.io, canyouseeme.org): check TCP 30333 against your public IP.
  • The authoritative check is the node itself: gpn_node --status shows tier: backbone once reachable, and (in opt-out mode) the console prints NOW DIALABLE.

If it still fails: confirm the rule is TCP (not UDP), the internal IP is current (DHCP may have moved it), the host firewall allows it, and the ISP is not blocking inbound ports (some block 30333; use another GPN_SEED_PORT).

Pull vs push — work behind NAT

A provider used to learn about its jobs only when the access point pushed them to the provider's heartbeat port (POST /assign on :8093). That needs an inbound port, which a CGNAT or locked-down router cannot give you — the node would sync, mine, and be reachable outbound, yet never receive a job.

The pull transport inverts it: the provider asks the access point for its own assignments (GET /assignments, a bounded long-poll) and writes them into the same local stores the claim loop already reads. Nothing downstream changes: claiming, inference, result return and settlement are identical, and the provider behind NAT now earns.

The poll also carries your capabilities (caps, read from your local /status over loopback), so the access point learns your models, GFLOPS, VRAM, GPU class and live active count without ever dialling your :8093. That is what lets a NAT'd provider actually be routed to — before this, an unreachable /status meant the box was pollable but never picked.

# ~/.gpn/node.toml — the only setting you need
ap_url = "http://gpn-testnet.duckdns.org:8092"

Off-chain escrow (payment channels) — AI jobs without a block wait

By default an AI job is escrowed per job on chain (create_job → claim → submit_result → complete_job), so it waits on the block clock (typically ~15–20 s, occasionally 60–140 s on a slow seal).

Channel mode locks a deposit once per provider and then moves the per-job payment off-chain as two signatures. Measured steady state on the dev fleet: ~0.2–0.4 s end-to-end for a short LLM answer, with zero per-job transactions. Design and guarantees: docs/design/design-offchain-escrow-channels.md (§11–18).

It is on by default and falls back per request to the on-chain path if anything is unavailable (provider doesn't serve /channel/job, the channel can't be opened, a signature fails), so enabling it can never lose a job.

How to become a seed / bootstrap node

A seed is a backbone node that is published as a bootstrap dial target. Nothing is registered and no permission is granted — a seed has no privileges.

What qualifies:

  • inbound-reachable on TCP 30333 with a stable public IPv4 (static, or a DDNS name kept current);
  • same genesis_hash, released unmodified binary, always-on and monitored; target ≥ 99.5% monthly reachability;
  • backbone tier with uptime_bps ≥ 9500 (95%) over the liveness window and reachable_count ≥ 3 distinct peer witnesses;
  • a published abuse/ops contact and a named maintainer.

How promotion works: the node announces its endpoint on-chain by itself. An off-chain exporter (gpn_seedlist, permissionless to run) reads pallet-gpn-liveness and publishes the top 16 eligible nodes by (uptime_bps, cumulative_online_blocks) to seeds.json, which every client fetches at startup. There is nothing to apply for; running a healthy dialable node is the application. Anyone can audit or re-publish the list from chain state.

The hardcoded 5-seed list is separate. Every client also ships with up to five compiled-in seed IPs as a DNS/HTTP-independent floor. Those five are a dedicated bootstrap set: separately operated cheap VPSes controlled and rotated by GPN, used only as dial targets — not co-located with the oracle operators. Inclusion is by invitation against the criteria above (distinct operators/jurisdictions, ≤2 changes per release), not by uptime ranking alone.

Ollama is a REQUIRED component (bundled installer + hard gate)

A GPN node is always miner AND AI provider. Ollama is therefore a first-class, required component, not an optional extra:

  • the installers ship inside the release package (scripts/install-ollama.ps1, scripts/install-ollama.sh, scripts/install-ollama-amd.sh), together with gpn-node.example.toml and README-FIRST-RUN.txt;
  • gpn_node probes GPN_OLLAMA on every start, and if nothing answers it runs the automated first-run bootstrap: install (winget / official installer / bundled script) → start ollama serve detached → wait for /api/tags → pull the baseline model;
  • if ollama is still unreachable, the node REFUSES TO START. It logs an actionable error, prints node=down(no ollama), and exits 69 (EX_UNAVAILABLE) so a supervisor/service manager reports the real cause. It never silently runs miner-only.

Updates — auto-update and the minimum-version cutoff

Short version: opt in and forget it, or update by hand — but a node that falls too far behind stops mining. Full detail: docs/updates.md.

# (default: on — this line is only needed to opt back in after disabling)
GPN_AUTO_UPDATE=1 gpn_node

# manual (the default): nothing is downloaded, ever
#   ...but when a release raises min_version this node will SYNC and NOT MINE

Auto-update (on by default; opt out with GPN_AUTO_UPDATE=0 / auto_update = false):

  • checks https://gpncoin.ai/releases.json at start and every GPN_UPDATE_CHECK_HOURS (default 6);
  • verifies an ed25519 signature over the manifest with the key compiled into the node — a forged manifest (or a compromised web host) is rejected before a single byte is downloaded;
  • verifies the artifact's sha256 twice: in memory after the download, and again from disk immediately before the swap;
  • stages it as gpn_node.new, keeps the old binary as gpn_node.bak, and swaps atomically;
  • restarts to run it. That is a short outage (seconds: children stop cleanly, sync resumes) — it is the only way to execute new code. Prefer to choose the moment? GPN_UPDATE_RESTART=0 stages it and applies it on your next restart.

The cutoff (not optional): every start — auto-update or not — the signed manifest's min_version is checked. Below it:

  !! UPGRADE REQUIRED — this node is 0.1.0, the network requires >= 0.2.0
  This node will SYNC ... but will NOT MINE and will NOT ANNOUNCE itself.

The supervisor launches the chain node with --no-seed --no-discoverable and GPN_STANDBY=1, which stops the proposer and the miner. The node keeps syncing, keeps its RPC, and can be upgraded in place. The last verified cutoff is cached in <base>/update/update-state.json, so it still applies if the manifest is unreachable.

Rollback: if a release is bad, stop the node, move gpn_node.bak back over gpn_node, and restart (§6 of docs/updates.md).

The on-chain half of the cutoff (a MinNodeVersion storage item) is staged, not applied: docs/design/design-min-node-version.md.

AMD / Radeon support (ROCm)

GPN is GPU-native and supports AMD as a first-class vendor alongside NVIDIA. Two independent things use the GPU, and they have different requirements:

Use Needs Notes
Mining (Ethash) an OpenCL ICD vendor-agnostic — AMD, NVIDIA, Intel all mine. Install rocm-opencl-runtime on Linux (then reboot).
Serving LLMs (ollama) an ollama-supported backend Linux: ROCm; Windows: limited → often CPU fallback.

GPU detection is automatic and vendor-agnostic. The heartbeat (gpn_provider_status) and the node probe the local GPU and advertise gpu_class (discrete/integrated/unknown), vram_mb, and an FP32 tflops estimate so the min-GPU gate (#19) and the scheduler route correctly:

  • Linux — nvidia-smi, then rocm-smi (--showproductname, --showmeminfo vram), then lspci + /sys/class/drm.
  • Windows — Win32_VideoController (Get-CimInstance / wmic) for name + AdapterRAM. ⚠️ Windows caps AdapterRAM at 4 GiB, so set --vram-mb (or VRAM_MB) to the real figure for big cards.

Override anything with --gpu-class/--tflops/--vram-mb (or the GPU_CLASS, TFLOPS, VRAM_MB env vars).

Serving LLMs on AMD (Linux — ROCm)

# 1) the OpenCL ICD (mining) + the ROCm runtime (ollama):
sudo apt install rocm-opencl-runtime          # mining; then reboot
# 2) bring ollama up on ROCm (installs, starts, pulls the baseline):
./scripts/install-ollama-amd.sh

Ollama's bundled ROCm supports a subset of AMD cards (RDNA2/RDNA3 — RX 6000/7000 series, plus some older GCN). If it errors with "unsupported gfx", pin the compute target before ollama serve:

export HSA_OVERRIDE_GFX_VERSION=11.0.0   # RX 7000 (gfx1100/1101/1102)
# export HSA_OVERRIDE_GFX_VERSION=10.3.0  # RX 6000 (gfx1030/1031/1032)
ollama serve

Confirm GPU inference (not CPU): ollama ps (the PROCESSOR column should say ROCm/GPU) — or grep -i 'inference compute' ~/.gpn/ollama.log.

Windows + AMD (ROCm is limited)

On Windows, ollama's ROCm support is limited/experimental. In practice an AMD Windows box either (a) runs ollama on the CPU — correct but slow, or (b) needs a DirectML/ROCm build if one exists for the card. Mining is unaffected (pure OpenCL). This is why an AMD Windows box may show high latency on LLM jobs even though it mines fine — set expectations (small models, quantized) and prefer Linux for full AMD GPU serving.

CPU-fallback caveat: when ollama cannot use the GPU it silently falls back to the CPU, giving ~10–50× lower token/s. The node still works and still mines; just budget latency accordingly.

Sync-robustness defaults (why your node won't wedge)

GPN has no finality gadget — the finalized head stays at #0. That breaks both of the things a node normally leans on to sync, so gpn_node bakes in the one reliable combination (on by default, overridable via GPN_NODE_ARGS / node_args):

Flag Why
--sync full fast/warp build their proof from a finalized block; with no finality they burst then stall early. (full is also the node default, but we pin it explicitly so a stray --sync fast can't re-introduce the wedge.)
--state-pruning archive The node default is 256, pruned relative to finality — i.e. it discards state almost immediately on GPN, so a peer that asks for it gets "State already discarded", the peer bans us, and our best block freezes. archive never discards state.
--blocks-pruning archive Same finality-relative problem for block bodies (default archive-canonical). archive keeps every body so we can always serve a syncing peer.

Archive is cheap here (the whole testnet DB is well under a gigabyte); there is no reason to prune on a chain this small.

⚠️ Legacy DB caveat — and the pinned base path. Substrate locks the state-pruning mode into the DB at first creation, and requesting archive on a DB that was created with the old 256 default hard-fails: Incompatible pruning modes [stored: Constrained { max_blocks: Some(256) }; requested: ArchiveAll].

So gpn_node now pins a single base path and uses it for both the DB check and the node's --base-path (resolution: GPN_BASE_PATH → config base_path → default C:\gpn\data on Windows / ~/.gpn/node on Unix). This matters because a node launched with no --base-path silently uses the OS-default data dir (%LOCALAPPDATA%\gpn-node.exe\data on Windows) — a guard that only inspected an explicit base path therefore looked at the wrong directory and forced archive onto a legacy DB → crash-loop.

The archive default is applied only when the DB is fresh, or when it carries the .gpn-pruning-archive marker gpn_node drops next to a DB it created with archive. For any existing legacy/unknown DB it requests no pruning flags (so the node's compiled defaults match the stored mode) and logs a clear warning — it can no longer crash-loop on Incompatible pruning modes. For backward-compat, if no DB exists at the pinned path but one exists at the OS-default path, the OS-default DB is detected and used (with a warning). Such a legacy DB must still be re-created (see the Troubleshooting entry below) before it can be stall-proof.

Disk headroom (why your chain can halt with a full disk)

On 2026-10-19 the root filesystem filled to 100% and the only symptom was a chain halt: the node mined a block but could not persist its header (ENOSPC), so its in-memory best chain kept a hash that could never be fetched again. Nothing warned beforehand.

  • Check it: df -h <your data dir> (Linux/macOS) or Get-PSDrive C (Windows). Keep ≥10% free (≈ 20 GB on a typical build box).
  • The heartbeat reports it: GET /status on the provider heartbeat (:8093) now includes disk_free_mb, disk_total_mb, disk_free_pct (probe of $GPN_DATA_DIR or $HOME; 0/null = probe unavailable, not full). The heartbeat also prints a ⚠ LOW DISK: line at startup below 10%. Point a monitor at disk_free_pct.
  • Build hosts: Rust target/debug is the usual culprit (it reached 217 GB here). Run cargo clean --profile dev — or cargo clean — regularly, and keep target/ on a different filesystem from the node's data directory where possible.
  • Recovery if it already halted: free space, then restart the node (systemctl --user restart gpn-fleet). Freeing space alone does not clear the stale in-memory best-chain hash.

What the supervisor does

  • Spawns each child with a label and forwards its stdout/stderr with a [node] / [heartbeat] / [provider] / [diffuse] / [ml] / [finetune] prefix.
  • Restarts a crashed child with bounded backoff (1s → 2s → … → 30s); the backoff resets once a child has been healthy for 60s. Every start / exit / restart is logged as [supervisor HH:MM:SS] <label>: ….
  • Stops all children gracefully on Ctrl-C / SIGTERM: each child gets SIGTERM, is waited on for up to 10s, then SIGKILLed, and the supervisor exits.
  • Prints one aggregated status line every status_secs (default 15s):
[status] node_count=6 node=up(pid 123) heartbeat=up(pid 456) provider=up(pid 789) diffuse=up(pid 790) ml=up(pid 791) finetune=up(pid 792) best=#107535

best is the node's best block, read cheaply from its own RPC (chain_getHeader); ? if the node's RPC isn't answering yet.

A node that failed the dialability gate with --require-backbone set is shown distinctly as node=down(not dialable, restarts N) (the child exited 78), with an actionable hint in the log — set GPN_PUBLIC_ADDR and forward the port. Without --require-backbone, a non-dialable node stays up and simply runs degraded.

Console encoding on Windows (emoji / mojibake)

gpn_node prints a few non-ASCII glyphs (warning signs, a sleep/zzz marker, the winner trophy, …). On a legacy Windows console these mojibake even with chcp 65001 (⚠️ shows as ΓÜá∩╕Å, 💤 as ≡ƒÆñ) because the text round-trips the PowerShell pipeline (e.g. Tee-Object) through the OEM code page.

The supervisor now sanitises every line it prints to ASCII when needed: known symbols map to readable tokens (⚠️ → !, 💤 → [zzz], 🏆 → [win], 📦 → [pkg]), dashes/ellipses map to -/..., and anything else becomes ?. Nothing ever mojibakes.

  • Default: ASCII mode is on for Windows, off for Linux/macOS (modern terminals render UTF-8 fine).
  • Force it on anywhere: pass --no-emoji, or set GPN_ASCII_LOG=1.
  • Force it off (keep emoji): set GPN_ASCII_LOG=0.
# plain ASCII on any console (e.g. a legacy WS2016/2019 box):
$env:GPN_ASCII_LOG = "1"
.\bin\gpn_node.exe --config .\gpn-node.toml
#   …or one-shot:  .\bin\gpn_node.exe --config .\gpn-node.toml --no-emoji

Watchdog — auto-recover a silently wedged node

GPN has no finality, so a node can stay p2p-connected while its best block silently freezes (see the Troubleshooting entry below). gpn_node watches for exactly this: it polls the node's own RPC (chain_getHeader → best number) every GPN_STALL_CHECK_SECS (default 60 s). If best is unchanged for more than GPN_STALL_SECS (default 300 s = 5 min) while at least one peer is connected, it logs a loud SYNC STALL alert and restarts the node child (SIGTERM → the supervisor restarts it with its normal backoff → it re-syncs).

It is deliberately conservative so it never fights healthy behaviour:

  • normal syncing advances best on every check → never triggers;
  • if the node's RPC isn't answering yet (startup / mid-restart) the clock is reset, not counted;
  • with zero peers it logs but does not restart (a peerless node can't sync anyway — that's a different problem);
  • after a restart it resets its timer, so it can't spiral into a tight kill loop.

Tune it with GPN_STALL_SECS (min 60) and GPN_STALL_CHECK_SECS (min 10).

Troubleshooting — node connected but not syncing

Symptom. The node shows peers at the p2p layer — system_peers lists them as FULL/AUTHORITY — but its best block is frozen while the network head keeps advancing. system_syncState shows currentBlock stuck. Logs may show State already discarded followed by Same block request multiple times. Banned, disconnecting — the sync peer bans the node, it has no other peer, and it never imports another block. This is the silent wedge.

Mechanism (why). GPN has no finality gadget — the finalized head is #0 forever. Two things then go wrong:

  1. Finality-relative pruning. The node's default pruning is --state-pruning 256 / --blocks-pruning archive-canonical, both measured from the finalized block. With finality pinned at #0, the node discards state and block bodies almost immediately. A peer that requests them gets "State already discarded", the request repeats, and the peer bans us.
  2. Finality-dependent sync modes. --sync fast / warp need a finalized block to build their state proof. With no finality they burst for a moment then stall early.

Because the node loses its only peer to a ban, it can no longer sync and its best block freezes — while still looking "connected" in the peer list.

Fix. Run with the reliable combination (which gpn_node now defaults to):

gpn-node --chain testnet --base-path ~/.gpn/node --sync full \
  --state-pruning archive --blocks-pruning archive …

If the node already has a (legacy 256) DB, the pruning mode is locked in and archive will hard-fail — re-create the data dir and let it re-sync, or import a fresh archive DB snapshot (fast — see docs/fast-sync.md):

# option A — re-sync from scratch (keep the node key / config):
mv ~/.gpn/node/chains/gpn_testnet/db ~/.gpn/node/chains/gpn_testnet/db.old
#   …then restart gpn_node: it creates a FRESH archive DB and full-syncs.

# option B — fast onboarding from a snapshot (recommended for a slow box):
scripts/gpn-snapshot.sh import --snapshot gpn-testnet-<tip>.tar.gz --base-path ~/.gpn/node --force

On Windows the legacy DB often lives at %LOCALAPPDATA%\gpn-node.exe\data (the OS default, used before the base path was pinned). gpn_node auto-detects it, but to migrate it cleanly: stop the gpn* processes, then either wipe chains/ (and let it re-sync) or import the archive snapshot with --base-path C:\gpn\data (see the fast-sync doc and docs/downloads.md for the snapshot URL).

Snapshot pruning marker. A gpn_snapshot export from a modern gpn-node is always an archive DB, so gpn_snapshot import now stamps the .gpn-pruning-archive marker by default — including for older snapshots whose manifest predates the marker feature and carries no pruning field. gpn_node then knows the imported DB is safe to run with --state-pruning archive (without the marker it conservatively leaves pruning untouched). Override with --pruning archive|none (e.g. --pruning none to import a legacy non-archive DB).

Deeper root cause: this failure mode only exists because GPN has no finality gadget. Archive pruning + --sync full are the correct workaround and make nodes robust today, but the real fix is to add finality at mainnet — see the finality-gadget design cross-reference in docs/mainnet-launch-runbook.md. Until then, assume no finality and never rely on finalized #> 0.

Troubleshooting — slow LLM jobs on a dual-stack / AAAA-laggy host (the /result stall)

Symptom. End-to-end text/image jobs through the access point work, but are slow — routinely 10–25s instead of <5s — even though the provider itself finishes inference in ~1s. The AP log shows it falling back to its ~11s on-chain reconcile instead of learning the result immediately.

Mechanism (why). When the AP and provider are co-located, the AP still advertises a public callback URL (GPN_PUBLIC_URL, e.g. http://gpn-testnet.duckdns.org:8092) and the provider POSTs the finished result back to {callback}/result/{id}. reqwest resolves that host with getaddrinfo(AF_UNSPEC) — both A and AAAA. If the host resolver does not answer AAAA (a common router/DNS quirk — e.g. 192.168.1.1), the AAAA leg blocks until it times out:

$ getent ahostsv6 gpn-testnet.duckdns.org    # hangs → rc=124 (timeout)
$ getent ahostsv4 gpn-testnet.duckdns.org    # instant → A record, rc=0
$ curl    http://gpn-testnet.duckdns.org:8092/health   # http=000 after ~8s (stalls)
$ curl -4 http://gpn-testnet.duckdns.org:8092/health   # http=200 in ~0.02s

Because the /result return is best-effort with a hard 5s budget, the stall makes it time out, the AP never learns the result off-chain, and it falls back to the slow reconcile — so e2e blows the <5s target. It is not an inference or chain problem; it is pure name resolution.

Fix (no root needed). GPN is now robust to this: the provider's /result (and the AP's /assign push) use a custom resolver that only issues A (IPv4) queries plus a bounded connect timeout, so a slow/absent AAAA can never block them (see gpn-agent/src/net.rs). No host DNS change is required.

Optional — remove the dependency entirely (co-located boxes). If your AP and provider run on the same machine, point the provider at loopback so no public lookup happens at all. In ~/.gpn/provider.env:

# either form (a bare base, or the full .../result URL) works:
GPN_RESULT_URL=http://127.0.0.1:8092
# GPN_AP_URL=http://127.0.0.1:8092

Precedence is GPN_RESULT_URL > GPN_AP_URL > the AP-advertised callback (remote providers keep using the advertised URL). The AP itself now advertises loopback automatically when its --listen is a wildcard bind (0.0.0.0:8092) and no GPN_PUBLIC_URL/GPN_AP_CALLBACK_URL/--callback-url is set.

Verify. Reproduce the raw stall and confirm the fix in one shot:

cd gpn-agent && cargo run --example dns_probe -- http://gpn-testnet.duckdns.org:8092/health
# dual-stack   ERROR in 8.000s: error sending request …   ← the stall
# ipv4-only    http=200 in 0.013s                        ← the fix

Real host fix (needs root — optional; the above makes GPN robust without it). Point the host resolver at a resolver that answers AAAA, then flush:

sudo resolvectl dns <iface> 1.1.1.1 192.168.1.1 && resolvectl flush-caches
# e.g. iface = enp42s0

Fault isolation / why separate processes

The supervisor deliberately keeps one process per part: an ollama/diffusion crash, an OOM in the AI stack, or a wedged inference never takes the chain node down — the supervisor restarts just that child. Folding everything into one binary is tracked separately (task #26, deferred).
