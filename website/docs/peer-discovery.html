GPN Peer Discovery

Verified against: chain spec 45 / release 0.3.11 — checked 2026-11-02 at block 236,986.

How a GPN node finds peers at startup — Bitcoin-style. This documents the seed sources, the seed-list wire format, how to host a seed, and the security model.

Historically a GPN node had exactly one way to find peers: a static --bootnodes <multiaddr> passed on the command line (or baked into the chain spec). That is a single point of failure. Discovery now layers four independent sources on top of it.

Implementation: gpn-node/node/src/discovery.rs (parsing / DNS / HTTP / persistence) and gpn-node/node/src/service.rs (prepare_network_config, the persistent-peer-store task and the on-chain discovery task).

Sources (all merged, deduplicated, best-effort)

At startup the effective bootnode set is the union of:

  1. Static bootnodes & hardcoded seeds — --bootnodes <multiaddr> / chain-spec bootnodes / the compiled-in network.json, which carries both bootnodes[] and Source A bootstrap_seeds[] (≤5 hardcoded IP dial targets, §"Source A" below). Kept first as the hard fallback — it works with no DNS, no HTTP and no chain (see design §3.0/§3.1).
  2. Persistent peer store (addrman) — <base-path>/gpn-peers.json. The node periodically snapshots the addresses of peers it is connected to and re-dials them on the next start.
  3. DNS seed — --bootnodes-dns <name> (repeatable).
  4. HTTP seed list — --bootnodes-url <url> (repeatable). Defaults to the registry's bootstrap_urls[] (Source B), else the live network directory at https://gpncoin.ai/seeds.json — no flag needed.

Source A — the hardcoded seeds (network.json → bootstrap_seeds[])

"bootstrap_seeds": [
  { "id": "seed-1", "ip4": "142.129.54.88", "port": 30333,
    "peer_id": "12D3KooWAFt…", "dns4": "gpn-testnet.duckdns.org",
    "operator": "gpn-core" }
]
  • ip4 is authoritative (a literal IPv4 is the cold-start path); dns4 is an optional alias in the same entry and is dialled as well, so an IP change survives a DNS update without shipping a client.
  • peer_id is mandatory: it is the real identity check (a dial to a wrong or hostile host fails the libp2p handshake). An entry without a usable peer id, or with neither ip4 nor dns4, is logged and skipped at load time.
  • Fewer than five entries is valid — "a floor of one is still a floor".
  • An operator override (~/.gpn/network.json / GPN_NETWORK_REGISTRY) may change identity fields but cannot blank this floor: empty bootstrap_seeds / bootstrap_urls in an override are filled from the compiled-in registry (network_registry::apply_bootstrap_floor).

Source B — network.json → bootstrap_urls[]

The default --bootnodes-url list, unioned (not replaced) across publishers. A failing URL is logged and skipped. seeds.json is produced by gpn_seedlist from on-chain liveness (docs/peer-discovery.md §"Publishing a seed list").

Sources are resolved independently. A source that is unreachable, malformed or slow is logged and skipped — it never aborts startup. Only entries that parse as a dialable libp2p multiaddress (i.e. end in /p2p/<peer-id>) survive the merge.

CLI flags

--bootnodes <MULTIADDR>...        # static (pre-existing), e.g. the hardcoded fallback
--bootnodes-dns <NAME>...         # resolve NAME's DNS TXT records as seeds
--bootnodes-url <URL>...          # fetch a published seed-list JSON
                                  # default: https://gpncoin.ai/seeds.json

--bootnodes-url replaces the default directory when given (pass several to union them); the compiled-in --bootnodes always remain as the last-resort fallback. The supervisor exposes the same setting as bootnodes_url in node.toml and as GPN_BOOTNODES_URL.

Refresh + last-good cache (a node does not re-read the list only once)

Startup resolution is a snapshot, so the node keeps reading it:

  • Cadence — every 15 minutes while it has fewer than 8 peers, otherwise hourly, with ±15 % (downward) jitter so a fleet started together does not hit the publisher in one burst. Consecutive failures multiply the wait (2×, 4×, 8×) and the wait is capped at 4 h, so a dead publisher is not hammered and never stops being retried.
  • Dialling — each refreshed list is shuffled before dialling (Fisher– Yates) and every entry is passed to add_known_address, so a list sorted by uptime cannot funnel the whole network onto the same three seeds.
  • Last-good cache — every successful fetch is written to <base-path>/gpn-seeds-cache.json ({updated_unix, multiaddrs[]}). If the publishers are all unreachable at startup, the node falls back to that cache and logs seed sources unavailable — using N cached seed(s). A cache older than 7 days is ignored rather than pinning the node to moved seeds; an empty fetch never overwrites a good cache.
  • GPN_SEED_REFRESH_SECS overrides the 15-minute cadence (floor 30 s, cap 4 h) — useful for testing an aggressive refresh.

On-chain discovery (GPN-native top-up)

Once the node has at least one connection, a background task reads two on-chain registries via the node's own chain client and dials the endpoints it finds:

  • Liveness::Endpoints — the endpoint each registered full node declared (gpn-liveness::register_fullnode), and
  • ComputeMarketplace::ProviderEndpoints — the endpoint each registered compute provider published.

Each endpoint is converted to a multiaddress (a libp2p multiaddr is used as-is; an http(s)://host:port, ws(s)://… or bare host:port becomes /dns4|ip4|ip6/…/tcp/<port>). Only endpoints that carry a peer id are dialable, so provider HTTP endpoints (which have none) are recorded but not dialed — best-effort by design. This runs after bootstrap deliberately: a brand-new node with zero peers has no way to trust on-chain data yet, so it must first reach the network through a static / DNS / URL / persisted peer, then top up. Startup is never blocked on it.

Seed-list wire format

A seed source yields a list of libp2p multiaddresses, each carrying the peer id in a trailing /p2p/<peer-id> component. JSON payloads may be either an object with a multiaddrs array:

{
  "multiaddrs": [
    "/dns4/node1.example.org/tcp/30333/p2p/12D3KooWAFtUNxc6RgC9rq5uSHXd5XUncEcPqp77UU98oN6hSVFo",
    "/ip4/203.0.113.7/tcp/30334/p2p/12D3KooW9ye8kXwMYT4vBJoJdCkM9VfRrcM7nGgqVDPq3Fy8i6xw"
  ]
}

or a plain array:

["/dns4/node1.example.org/tcp/30333/p2p/12D3Koo…", "/ip4/203.0.113.7/tcp/30334/p2p/12D3Koo…"]

Non-JSON bodies (and each DNS TXT record) are also accepted as newline-separated multiaddr strings — one multiaddr per line; blank lines and # comments are ignored:

# GPN seed list — example.org
/dns4/node1.example.org/tcp/30333/p2p/12D3KooWAFt…
/ip4/203.0.113.7/tcp/30334/p2p/12D3KooW9ye…

The peer id after /p2p/ is what lets a client dial safely: it is verified during the libp2p handshake, so a wrong or malicious address simply fails to connect — it cannot impersonate a node.

The persistent peer store (gpn-peers.json) uses the same object form, so it is itself a valid seed source you can inspect, copy or hand to another node.

The network directory (https://gpncoin.ai/seeds.json)

The default seed source is a Cloudflare Worker in this repo (worker/worker.js, deployed as the gpn-coin Worker that also serves this site). It is the GPN equivalent of a DDNS name for the whole network: nodes ask one stable hostname "who is up right now" instead of every operator tracking every address.

Endpoints

URL Body
GET https://gpncoin.ai/seeds.json JSON (the shape below)
GET https://gpncoin.ai/bootnodes.txt the dialable multiaddrs, one per line
GET https://gpncoin.ai/seeds.txt alias of /bootnodes.txt

Response

{
  "network": "GPN Public Testnet",
  "chain_id": "gpn_testnet",
  "genesis": "0xb8e4636a65d0c812abb437c38dd7e937bd7c3355c54c54d63060f26a33519a5c",
  "updated_at": "2026-10-19T22:00:00.000Z",
  "updated": 1760990400,
  "ttl": 60,
  "source": "static+ap",
  "live_providers": 1,
  "multiaddrs": [
    "/dns4/gpn-testnet.duckdns.org/tcp/30333/p2p/12D3KooWAFtUNxc6RgC9rq5uSHXd5XUncEcPqp77UU98oN6hSVFo"
  ],
  "nodes": [
    { "multiaddr": "…", "peer_id": "12D3Koo…", "role": "seed", "source": "compiled-in" },
    { "endpoint": "http://203.0.113.7:8093/status", "multiaddr": "/ip4/203.0.113.7/tcp/8093",
      "peer_id": null, "role": "provider", "source": "ap", "address": "5ENq…" }
  ],
  "publisher": "gpncoin.ai"
}
  • multiaddrs is what gpn-node consumes; the rest is metadata for humans and tooling. source is static+ap, static+ap-empty, or static-fallback (the AP was unreachable) — the endpoint never returns 5xx for a discovery failure.
  • genesis/chain_id let a client reject a list for the wrong network without parsing every address.
  • nodes[] also carries providers that only publish an HTTP status_url: they have no /p2p/<peer-id>, so they appear for tooling but are not added to multiaddrs (the node cannot dial a peer without a peer id).

Provider peer-id publication. A provider can make itself dialable by publishing its libp2p identity alongside its heartbeat (see Publishing a provider as a dialable peer). When it does, the directory emits a real multiaddr for it:

{
  "multiaddrs": [
    "/dns4/gpn-testnet.duckdns.org/tcp/30333/p2p/12D3KooWAFt...",
    "/ip4/203.0.113.7/tcp/30333/p2p/12D3KooW9ye..."
  ],
  "nodes": [
    { "multiaddr": "/ip4/203.0.113.7/tcp/30333/p2p/12D3KooW9ye...",
      "peer_id": "12D3KooW9ye...", "role": "provider", "source": "ap",
      "endpoint": "http://203.0.113.7:8093/status", "address": "5ENq..." }
  ]
}

Duplicate addresses (a provider that is also a compiled-in seed, or two heartbeats reporting the same listener) are collapsed - one entry per multiaddr.

Where the live half comes from. The Worker fetches GET /providers from the access point (wrangler var AP_URL), keeps entries the AP reports as healthy, converts each status_url to a multiaddr, and merges. The result is cached in-isolate for 60 s and served with Cache-Control: public, max-age=60.

The AP listens on a non-standard port (:8092), which the Workers fetch() API refuses. The Worker therefore tries fetch() first (so an HTTPS ingress always wins and is the recommended production setup — e.g. a Cloudflare Tunnel mapping https://ap.gpncoin.ai → 127.0.0.1:8092) and falls back to a raw HTTP/1.1 GET over cloudflare:sockets, which can reach any port. That fallback is what keeps the directory live today, with no extra infrastructure.

Deployment. The Worker and the site are one deployment: pushing to main rebuilds it and https://gpncoin.ai/seeds.json goes live (the custom domain is already attached). Before that build lands — or on a fork without the domain — the same endpoint is on the workers.dev hostname of the gpn-coin Worker. Confirm with curl -s https://gpncoin.ai/seeds.json | head; "source": "static+ap" means the live merge worked, static-fallback means the AP was unreachable (the list is still valid).

Publishing a provider as a dialable peer

The access point's /providers list only contains what each provider's heartbeat (gpn_provider_status, :8093) reports. Historically that was status_url + SS58 address - enough to monitor a box, not enough to dial it. A provider now also publishes its node's libp2p identity:

1. The provider reads its own node over JSON-RPC (GPN_ENDPOINT, default ws://127.0.0.1:9944):

RPC Used for
system_localPeerId the 12D3Koo... peer id
system_localListenAddresses /ip4/<public>/tcp/30333, ...

2. It chooses what to publish. GPN_PUBLIC_ADDR / --public-addr (/ip4/1.2.3.4/tcp/30333 or 1.2.3.4:30333) is authoritative when set - a box listening on 0.0.0.0 cannot know its own public IP. Without it, every globally routable listen address is published; loopback, RFC1918, CGNAT and link-local listeners are discarded rather than advertised as if dialable.

3. GET /status gains these fields (all optional: omitted - never null - when the node RPC cannot be read):

{
  "peer_id": "12D3KooWAFtUNxc6RgC9rq5uSHXd5XUncEcPqp77UU98oN6hSVFo",
  "multiaddrs": ["/ip4/203.0.113.7/tcp/30333/p2p/12D3KooWAFt..."],
  "p2p_port": 30333,
  "listen_addrs": ["/ip4/0.0.0.0/tcp/30333", "/ip4/127.0.0.1/tcp/30333"]
}

The peer id + listen addresses are cached for 60 s (a failure is retried after 10 s, because the heartbeat may start before the node RPC is up). A peer-id lookup failure never fails the heartbeat - the rest of /status is unaffected.

4. The AP validates and relays. GET /providers entries gain peer_id, multiaddrs[] and p2p_port:

{ "providers": [
  { "status_url": "http://203.0.113.7:8093/status", "address": "5ENq...",
    "peer_id": "12D3KooWAFt...",
    "multiaddrs": ["/ip4/203.0.113.7/tcp/30333/p2p/12D3KooWAFt..."],
    "p2p_port": 30333, "healthy": true }
] }

This is a public directory, so the AP does not relay arbitrary strings: the peer id must be a base58 12D3Koo.../Qm... id; a multiaddr must be a /proto/value/... chain of whitelisted protocols (ip4 ip6 dns dns4 dns6 tcp udp quic quic-v1 p2p tls sni ws wss) with a numeric port and a trailing /p2p/<peer-id>; and that trailing id must equal the peer_id in the same snapshot. Anything else is dropped (the port alone may survive as metadata).

5. The Worker merges. A provider with a peer id and a public p2p address is written into multiaddrs (dialable, deduplicated against the compiled-in seeds). If it reports only peer_id + p2p_port - the normal NAT case, where it listens on 0.0.0.0 - the Worker combines the port with the host the AP already reached it on (status_url) to form /ip4/<host>/tcp/<p2p_port>/p2p/<peer_id>.

Fallback. A provider that cannot publish a peer id (no RPC access, no GPN_PUBLIC_ADDR and no routable listener, or a failed validation) stays in nodes[] with endpoint only, exactly as before: listed for humans/tooling but never added to multiaddrs. A server that can reach its node RPC but does not know its own public IP should set GPN_PUBLIC_ADDR - that is the one piece the provider cannot infer.

The gpn_node supervisor does not pass --endpoint to the heartbeat child yet; it inherits GPN_ENDPOINT from the environment and otherwise defaults to ws://127.0.0.1:9944, which is correct when the node runs on the same box.

Hosting a seed

Any HTTP host works (static file, object store, small service):

  1. Publish the JSON at a stable URL, e.g. https://gpncoin.ai/seeds.json.
  2. Ensure it is reachable from the machines that run GPN nodes.
  3. Operators add it with --bootnodes-url https://… — or just point at the default directory, which is already wired in.

Generating the list from the chain (gpn_seedlist)

Don't hand-curate it. gpn_seedlist derives the list from on-chain liveness, so anyone can audit — or re-publish — the same result:

gpn_seedlist ws://127.0.0.1:9944 --out /srv/www/seeds.json --ttl 300

Promotion is earned, not asserted: a node is published only when the chain shows it is reachable (≥3 distinct bonded witnesses — Liveness::WitnessCounts), is reliably online (uptime ≥ 95%), was confirmed online in the last window, and has a dialable endpoint (a real /p2p/<peer-id> multiaddr — placeholders and http://…/status URLs are dropped). Survivors are ranked by uptime and the top 16 published; the write is atomic (temp + rename), so a cron publisher can never serve a half-written file.

gpn_seedlist --print                       # dry run: who qualifies, and why not

An empty list is a valid publication (nobody qualifies yet); the tool only exits non-zero when the chain is unreachable, so a cron publisher fails loudly instead of replacing a good list with []. Publishing needs no privileges — a captured publisher still cannot inject a node, because peers verify the libp2p handshake and the genesis hash.

Run it from cron every few minutes (the ttl field tells clients how long to cache). Set --min-witnesses/--min-uptime-bps only if you deliberately want a looser/tighter policy, and say so where you publish.

A DNS seed is a hostname whose TXT records contain seed lists:

$ dig +short TXT seed.example.org
"\"/ip4/203.0.113.7/tcp/30333/p2p/12D3KooW9ye…\""

Regenerate it from your node inventory whenever peers change (a DNS provider with an API, or a tiny cron job, both work).

TLS: https:// seed sources are fetched natively (rustls + webpki roots — already in the node's dependency graph). http:// sources still use the HTTP-only client. Both are best-effort and time-bounded; no TLS stack is required on the host.

Security model

  • Run several independent seeds. A single DNS seed or a single seed URL is a centralization and censorship point: whoever controls it can eclipse the node from the network. Operate at least two independent DNS seeds and two independent HTTP seed sources, ideally on separate infrastructure/providers.
  • Keep the compiled-in bootnode as the hardcoded fallback. Pass it via --bootnodes (or bake it into network.json); never rely solely on remote seeds.
  • Peer identity is content-addressed. Because every seed entry ends in /p2p/<peer-id> and libp2p verifies that id during the handshake, an attacker who tampers with a seed list cannot impersonate an existing node — they can at worst redirect you to nodes they control, which is why several independent seeds matter.
  • Seed list poisoning is limited. Invalid entries are dropped; duplicate entries are deduplicated; the effective set is bounded by the persisted-store cap.
  • Genesis still rules. Discovery does not change the network identity model: a node is on a network iff its genesis matches. Connecting to a peer on a different network is harmless (it is rejected during the handshake).
